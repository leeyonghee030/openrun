# OpenRun 기술결정

> 상태: **초안** (측정 결과 칸은 4~5주차에 채운다)
> 원칙: 말이 아니라 **k6 측정 수치**로 근거를 남긴다. 결과 표는 이후 트러블슈팅 문서와 README에 재사용한다.

## 1. 대기번호 채번 방식 비교

### 1-1. 문제 정의
한 팝업에 동시에 여러 명이 접수해도 대기번호가 **중복 없이, 접수 성공한 건마다 빠짐없이** 발급되어야 한다. (NF-1)
번호는 팝업별·당일 기준 1부터 증가하고, 취소돼도 재사용하지 않는다. (용어 3장, R-7)

### 1-2. 비교 기준 (모든 방식에 같은 k6 시나리오 적용)
| 지표 | 내용 |
|---|---|
| 정확성 | 중복 번호 수, 번호가 없는 접수 건수 |
| 실패율 | 예외, 타임아웃, 재시도 초과 건수 |
| 성능 | TPS, p95 응답시간 |
| 부하 조건 | 같은 팝업에 동시 접수 10 / 100 / 500 VU |

- 번호는 "발급 순서"이지 "연속 순번"이 아니다. 취소하면 번호에 구멍이 생기므로 **누락은 번호 빈칸이 아니라 "접수 성공했는데 번호가 없는 건"으로 정의**한다.
- "내 앞 팀 수"는 `활성 상태(WAITING, CALLED)이면서 내 번호보다 작은 건수`로 계산한다. (저장하지 않음)
- 방식을 `채번 전략` 인터페이스로 분리해 구현체만 바꿔 같은 테스트를 돌린다.

### 1-3. 방식별 가설과 결과

#### (1) DB `MAX+1` (락 없음)
- 구현: 해당 팝업·당일의 MAX 번호를 조회하고 +1로 INSERT
- 가설: 동시 요청이 같은 MAX를 읽어 **번호가 중복**된다. 이 중복 건수가 실험의 출발점이다.
- 측정은 두 가지로 나눈다: ① 유니크 제약 없음 → 중복 건수 확인, ② (팝업, 날짜, 번호) 유니크 제약 있음 → 중복 대신 예외 실패율 확인
- 결과: _측정 예정_

#### (2) 비관적 락
- 구현: 팝업 행(또는 카운터 컬럼)을 `SELECT ... FOR UPDATE`로 잠그고 번호 증가
- 가설: 정확하지만 팝업 단위로 직렬화되어 대기 시간이 늘고, 커넥션 풀 고갈과 락 타임아웃 위험이 있다.
- 주의: MAX 조회에 락을 거는 방식은 빈 결과에서 갭 락 문제가 생겨 비교가 불공정해진다. **팝업 행에 카운터를 두고 그 행을 잠그는 방식**으로 구현한다.
- 결과: _측정 예정_

#### (3) 낙관적 락
- 구현: 팝업 카운터에 `@Version`을 두고 충돌 시 재시도
- 가설: 경합이 낮으면 유리하지만, 같은 팝업에 몰리면 재시도가 폭증해 실패율이 오른다. 오픈런 상황은 경합이 높은 쪽이다.
- 결과: _측정 예정_

#### (4) Redis `INCR`
- 구현: `INCR queue:{storeId}:{날짜}` 로 번호 발급 후 DB에 INSERT
- 가설: 빠르고 원자적이다. 대신 **Redis와 DB 사이 정합성**, Redis 장애 시 카운터 복구라는 비용이 생긴다.
- 결과: _측정 예정_

## 2. Redis와 DB 역할 분담 (초안, 5주차에 확정)

### DB (MySQL) = 원본, 모든 영속 데이터
- 회원, 팝업, 영업 스케줄(요일별 + 날짜별 예외), 접수 상태
- 대기 레코드: 번호, 상태, 호출 시각, 입장/취소/노쇼 시각
- 회원의 연속 노쇼 횟수, 제재 종료일

### Redis = 빠른 연산용. 날아가도 DB로 복구할 수 있는 것
- 대기번호 카운터: `INCR queue:{storeId}:{날짜}` (날짜가 키에 들어가므로 영업일마다 자연스럽게 1부터 시작)
- (선택) 같은 (회원, 팝업)의 중복 접수 방지용 분산 락 (Redisson)
- (선택) SSE 알림 전달용 pub/sub

### 규칙
- Redis 장애·유실 시 카운터는 **DB의 해당 팝업 당일 MAX 번호**로 복구한다.
- 접수 INSERT의 최종 책임은 DB이고, (팝업, 날짜, 번호) 유니크 제약은 Redis를 써도 안전장치로 유지한다.

## 4. 테이블 생성 방식 (결정 11-16)
- 결정: `ddl-auto`(엔티티 기반)
- 이유: 엔티티 하나로 관리, 학원 방식과 동일
- 생성 컬럼(`is_active`)은 `columnDefinition`으로 처리. 개발은 `update`, 운영은 배포 때 다시 정한다

## 5. enum 컬럼 타입 (결정 11-17)
- 문제: Hibernate 7(Boot 4)은 MySQL에서 `@Enumerated(STRING)` 필드를 MySQL `ENUM` 타입으로 만든다. `ddl-auto: update`는 기존 컬럼을 바꾸지 않으므로, enum 값을 추가하면 INSERT가 실패하고 `ALTER TABLE`이 필요하다.
- 결정: enum 필드에 `@JdbcTypeCode(SqlTypes.VARCHAR)`를 붙여 ERD대로 `VARCHAR(10)`으로 만든다.
- 결과: Hibernate가 `CHECK (컬럼 in (...))` 제약을 함께 만든다. 잘못된 값을 DB가 막아 주므로 유지한다.
- 주의: enum 값을 추가·변경할 때는 CHECK 제약도 `ALTER TABLE`로 함께 고친다. (`update`는 CHECK를 바꾸지 않는다)
- 적용: users(`provider`, `role`, `status`), stores(`status`, `accept_status`), waitings(`status`)

## 6. 테스트 데이터 격리 (결정 11-18)
- 문제: `@SpringBootTest`는 기본 설정을 그대로 읽어 개발 DB(`openrun`)에 붙는다. 테스트 데이터가 개발 데이터와 섞이고, 실행할 때마다 쌓인다.
- 결정: ① 테스트 전용 스키마 `openrun_test` + ② 테스트 클래스에 `@Transactional`(끝나면 롤백). 둘 다 쓴다.
- 이유:
  - 스키마 분리로 개발 데이터를 건드리지 않는다.
  - 롤백으로 테스트끼리 데이터가 쌓이지 않는다.
  - 4주차 동시성 테스트는 여러 스레드가 각자 커밋해야 해서 롤백이 통하지 않는다. 그때도 개발 DB를 지키려면 스키마 분리가 미리 필요하다.
- 방법:
  - `src/test/resources/application-test.yaml`에서 `spring.datasource.url`의 DB 이름만 `openrun_test`로 덮어쓴다. 계정·비밀번호는 기본 설정(`.env`)을 그대로 물려받는다.
  - 테스트 클래스에 `@SpringBootTest` + `@ActiveProfiles("test")` + `@Transactional`.
  - 스키마는 root로 한 번 만든다: `CREATE DATABASE openrun_test;` `GRANT ALL PRIVILEGES ON openrun_test.* TO 'openrun'@'%';` 테이블은 `ddl-auto`가 만든다.
- 확인: 리포지토리 테스트 3개 통과 후 `openrun_test`에 테이블 3개 생성, 데이터 0건. `openrun`의 데이터 수는 그대로.
- 남은 일: 4주차 동시성 테스트(롤백 불가)의 데이터 정리 방법은 그때 정한다.
