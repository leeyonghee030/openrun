# OpenRun 요구사항

> 상태: **초안** (✅ 확정 / ❓ 확인 필요)
> 서비스 성격: 예약이 아니라 **현장 원격 줄서기** (테이블링, 캐치테이블 방식)

## 1. 서비스 흐름

```
[현장] 가게 태블릿(가게 계정으로 로그인)에서 손님이 전화번호 입력
   → 인원 선택(1~4명) → 대기 등록 (처음이면 자동 가입)
   → 대기번호 발급 + "내 앞에 N팀" 표시
   → (대기 중 자유롭게 이동) 앞 5팀 남으면 알림
   → 운영자가 호출 → 호출 알림 → 제한 시간 안에 입장
   → 입장 확인 / 안 오면 운영자가 노쇼 처리 → 다음 팀 호출
```

## 2. 사용자 구분

| 구분 | 설명 |
|---|---|
| 일반 사용자 (USER) | 팝업 조회, 가게 태블릿에서 전화번호로 대기 등록, 대기 취소, 내 순번 확인 |
| 가게측 (STORE) | 자기 가게의 대기 현황 확인, 태블릿으로 손님 대기 등록 접수, 다음 팀 호출, 입장 처리, 노쇼 체크, 접수 열기/마감. 가게 1곳당 계정 1개 |
| 운영자 (ADMIN) | 서비스 운영자. 전체 가게 관리, 가게측 가입 승인 |
| 면접관 (데모) | 데모 계정으로 로그인해 위 기능을 체험. 데모 패널 사용 |

## 3. 용어 (헷갈리지 않게 구분)

- **대기번호**: 등록할 때 받는 번호표. 한 번 받으면 바뀌지 않음. 팝업별, 당일 기준 1부터 증가. 취소돼도 재사용하지 않음.
- **순번 (내 앞 팀 수)**: 지금 내 앞에 몇 팀이 남았는지. 취소/호출이 일어나면 계속 줄어듦. 저장하지 않고 매번 계산한다.
- **팀**: 한 번의 대기 등록 단위. 인원 1~4명.

## 4. 대기 상태

```
WAITING(대기중) ──호출──▶ CALLED(호출됨) ──입장 확인──▶ ENTERED(입장완료)
    │                        │  └─운영자 노쇼 체크──▶ NO_SHOW(노쇼)
    └──사용자 취소──▶ CANCELED(취소됨) ◀──사용자 취소──┘
```

- 활성 상태 = WAITING, CALLED. 이 두 상태일 때만 "대기 중"으로 본다.
- 종료 상태 = ENTERED, CANCELED, NO_SHOW. 되돌릴 수 없다.

## 5. 기능 요구사항

### 5-1. 회원 (Core)
| ID | 요구사항 |
|---|---|
| U-1 | 손님(USER)은 가게 태블릿에서 처음 대기를 등록할 때 전화번호로 자동 가입된다. 별도의 회원가입 화면은 없다. |
| U-2 | 손님은 전화번호와 인증번호(데모는 가짜 인증)로 로그인하면 JWT를 받는다. STORE·ADMIN은 아이디/비밀번호로 로그인한다. |
| U-3 | 역할은 USER / STORE / ADMIN으로 나뉜다. ADMIN 계정은 초기 데이터로 만든다. |
| U-4 | 가게측은 별도로 가입한다. 가입하면 승인대기 상태가 되고, ADMIN이 확인 후 승인해야 가게 운영 기능을 쓸 수 있다. (구현 시점은 일정에 따라 정하고, 먼저는 초기 데이터로 대체 가능) |
| U-5 | STORE는 자기 가게의 대기·접수 상태만 다룰 수 있다. (남의 가게 접근 금지) |
| U-6 | 회원은 탈퇴할 수 있다. 진행 중 대기가 없으면 바로, WAITING만 있으면 취소 안내 후 확인하면 취소하고 탈퇴, CALLED가 있으면 탈퇴할 수 없다. (Core, 맨 뒤 순서로 구현) |

### 5-2. 팝업스토어 (Core)
| ID | 요구사항 |
|---|---|
| P-1 | 사용자는 팝업 목록과 상세(이름, 주소, 운영 시간, 현재 대기 팀 수)를 볼 수 있다. |
| P-2 | 가게는 현장 태블릿에 STORE 계정으로 로그인해 **접수 화면**을 열어 둔다. 손님은 이 화면에서 전화번호와 인원을 입력해 대기를 등록한다. 등록은 가게 계정만 할 수 있어서, 현장에 있다는 확인을 대신한다. (QR 토큰은 사진 공유로 뚫려 폐지) |
| P-3 | 팝업은 접수 상태(접수중 / 마감)를 가진다. |
| P-4 | (Optional) 운영자는 요일별(평일/주말/요일 개별) 접수 시간을 설정할 수 있고, 해당 시간에 접수가 자동으로 열리고 닫힌다. |
| P-5 | (Optional) 운영자는 특정 날짜에 예외(조기 오픈, 조기 마감, 휴무)를 설정할 수 있다. |
| P-6 | 팝업은 "날짜 바뀌는 시각"을 가진다. 기본 00:00(자정)이고, 자정을 넘겨 마감하는 팝업은 마감 시각으로 설정한다. 이 시각 전의 접수는 전날로 본다. |

### 5-3. 대기 (Core, 프로젝트의 핵심)
| ID | 요구사항 |
|---|---|
| W-1 | 손님은 팝업이 **접수중**이고 **제재 중이 아닐 때**, 가게 태블릿에서 전화번호와 인원(1~4명)을 입력해 대기를 등록할 수 있다. |
| W-2 | 등록하면 대기번호가 발급된다. 동시에 몇 명이 등록해도 번호는 중복·누락되지 않는다. |
| W-3 | 한 사용자는 같은 팝업에 활성 대기를 1개만 가질 수 있다. (연타, 탭 중복 포함) |
| W-4 | 사용자는 내 대기번호, 내 앞 팀 수, 상태를 조회할 수 있다. |
| W-5 | 사용자는 WAITING / CALLED 상태에서 대기를 취소할 수 있다. 취소하면 뒤 팀들의 순번이 당겨진다. |
| W-6 | 취소 후 다시 등록하면 새 대기번호를 받고 맨 뒤로 간다. |
| W-7 | 운영자는 다음 팀을 호출할 수 있다. (대기번호가 가장 작은 WAITING 팀이 CALLED로 바뀐다) |
| W-8 | 운영자는 호출된 팀의 입장을 확인할 수 있다. (CALLED → ENTERED) |
| W-9 | 운영자는 호출된 팀을 노쇼로 체크할 수 있다. (CALLED → NO_SHOW) 체크하면 다음 팀이 호출된다. (W-7과 같은 동작, 호출 알림 발송) 시스템은 자동으로 노쇼 처리하지 않는다. |
| W-9a | 호출 후 제한 시간(기본 5분)이 지나면 운영자 화면에 "5분 경과"를 표시한다. (표시만 하고 상태는 바꾸지 않는다) |
| W-10 | 운영자는 현재 대기 팀 목록과 상태별 개수를 조회할 수 있다. |
| W-11 | 운영자는 언제든 팝업 접수를 수동으로 열거나 마감할 수 있다. (조기 마감 포함) 마감하면 새 등록은 막지만 기존 대기는 유지된다. P-4, P-5를 도입하면 적용 우선순위는 수동 조작 > 날짜별 예외(P-5) > 요일별 기본(P-4). Core에서는 수동 열기/마감만 구현한다. |

### 5-4. 알림 (Core)
| ID | 요구사항 |
|---|---|
| N-1 | 내 앞 팀 수가 기준값(기본 5팀) 이하가 되면 알림을 받는다. (한 번만) |
| N-2 | 호출되면 알림을 받는다. |
| N-3 | 알림은 `NotificationSender` 인터페이스로 분리하고, 구현은 SSE(화면 실시간 표시)와 로그 두 가지로 한다. |

### 5-5. 노쇼 제재
| ID | 요구사항 |
|---|---|
| B-1 | 회원별 연속 노쇼 횟수를 기록한다. 정상 입장(ENTERED)하면 0으로 리셋한다. 사용자가 직접 취소(CANCELED)해도 횟수는 바뀌지 않는다. |
| B-2 | 연속 노쇼 3회, 4회째에 해당 회원에게 경고 알림을 보낸다. (`NotificationSender` 사용) |
| B-3 | 연속 노쇼 5회째가 되면 다음날부터 7일간 신규 대기를 등록할 수 없다. 이미 걸려 있던 대기는 유지한다. |
| B-4 | 제재 기간이 끝나면 연속 노쇼 횟수를 0으로 리셋한다. |

### 5-6. 데모 패널 (Core)
| ID | 요구사항 |
|---|---|
| D-1 | 면접관은 가입 없이 데모 계정(일반/운영자)으로 원클릭 로그인할 수 있다. |
| D-2 | 데모 모드에서는 로그인 인증번호를 가짜(로그 출력 또는 고정값)로 처리한다. |
| D-3 | "가상 대기자 N명 생성" 버튼으로 대기열을 채울 수 있다. |
| D-4 | "동시 등록 N명" 버튼으로 동시 요청을 보내고, 번호 중복 0건·누락 0건 결과를 보여준다. |
| D-5 | "다음 팀 호출" 버튼으로 내 순번이 줄어드는 과정을 볼 수 있다. |
| D-6 | 데모에서는 호출 경과 표시 시간(W-9a)을 30초로 줄일 수 있다. |
| D-7 | 데모 데이터 초기화 버튼이 있다. |

## 6. 비즈니스 규칙 요약

| ID | 규칙 | 상태 |
|---|---|---|
| R-1 | 팀 인원은 1~4명 | ✅ |
| R-2 | 한 사용자는 같은 팝업에 활성 대기 1개 | ✅ |
| R-3 | 취소 후 재등록은 맨 뒤 | ✅ |
| R-4 | 호출 후 5분이 지나면 운영자 화면에 경과 표시. 노쇼 처리는 운영자가 직접 | ✅ (설정값) |
| R-5 | 로그인 인증번호 유효 시간 | ❓ 값은 설정으로 빼고 정함 (데모는 가짜 인증) |
| R-6 | 알림 기준 앞 5팀 | ✅ (설정값) |
| R-7 | 대기번호는 팝업별·당일 1부터 증가. 날짜는 자정 기준이고, 자정을 넘겨 마감하는 팝업은 그 마감 시각 기준 (P-6) | ✅ |
| R-8 | 전화번호 계정으로만 등록 가능 (처음이면 자동 가입, 비회원 불가) | ✅ |
| R-9 | 서로 다른 팝업에는 동시에 대기 가능 (같은 팝업은 1개) | ✅ |
| R-10 | 연속 노쇼 5회 시 다음날부터 7일간 신규 대기 불가. 정상 입장 시와 제재 종료 시 횟수 리셋 | ✅ |
| R-11 | 접수 상태 우선순위: 수동 조작 > 날짜별 예외 > 요일별 기본 (Optional, P-4·P-5 도입 시) | ✅ |

## 7. 비기능 요구사항 (포트폴리오의 성공 기준)

| ID | 목표 | 확인 방법 |
|---|---|---|
| NF-1 | 동시 등록 N건에서 **대기번호 중복 0건, 누락 0건** | JUnit 동시성 테스트 + k6 |
| NF-2 | 같은 사용자의 동시 중복 등록이 **1건만 성공** | JUnit 동시성 테스트 |
| NF-3 | 대기번호 채번 방식별(DB MAX+1 / 비관적 락 / Redis) 처리량·응답시간 비교표 작성 | k6 |
| NF-4 | 두 운영자가 동시에 호출해도 **같은 팀이 두 번 호출되지 않음** | JUnit 동시성 테스트 |
| NF-5 | 핵심 로직(채번, 상태 전이, 노쇼 처리) 단위 테스트 | JUnit |

수치 목표(예: p95 응답시간)는 k6로 먼저 측정한 뒤 현실적인 값으로 정한다.

## 8. 보안 고려사항

### 처음부터 반영 (Core)
| 항목 | 내용 |
|---|---|
| 인증/인가 | JWT 인증. 가게 운영 API는 STORE만(자기 가게만), 승인·전체 관리 API는 ADMIN만 허용 |
| **본인 데이터만 접근** | 남의 `waitingId`로 조회·취소가 되면 안 됨. 서비스에서 "이 대기가 내 것인가" 반드시 검증 (IDOR) |
| 비밀번호 | STORE·ADMIN의 비밀번호는 BCrypt 해시 (학원에서 사용한 방식). 손님은 비밀번호가 없다 |
| 시크릿 | JWT 비밀키, DB 비밀번호는 `.env`/환경변수. 코드·깃에 올리지 않음 |
| 입력 검증 | 인원 1~4, 좌표 범위 등을 서버에서 Bean Validation으로 검증. 화면 검증을 믿지 않음 |
| 현장 확인 | 등록 API는 STORE 계정만 호출할 수 있다(가게 태블릿). 손님은 전화번호만 입력하므로 **남의 번호로 대기를 거는 도용은 완전히 막지 못한다**는 한계를 문서에 명시. 완화: 현장 태블릿에서만 입력 가능, 제재는 연속 5회부터이고 3·4회에 경고 |
| 에러 응답 | 스택트레이스, SQL 오류를 응답에 노출하지 않음 |
| 위치 정보 | 수집하지 않음 (가게 태블릿 등록이 현장 확인을 대신하므로 위치가 필요 없음) |
| 수집 정보 | 손님은 전화번호(계정 식별용)만 수집, 이메일은 받지 않음. 전화번호는 개인정보라 탈퇴 시 파기(`withdrawn_{id}`로 변경). 알림이 SSE/로그라서 문자 발송에는 쓰지 않음 |
| 인프라 | Docker의 MySQL, Redis 포트는 로컬 접속만 허용. 배포 시 외부 노출 금지 |
| 템플릿 | Mustache의 `{{ }}`(자동 이스케이프)만 쓰고 `{{{ }}}`는 쓰지 않음 (XSS) |

### 데모 모드 관련 (놓치기 쉬움)
- 가짜 인증번호와 데모 패널 API가 **운영 보안 구멍이 되지 않게** 한다. 데모 프로파일(`demo`)에서만 활성화하거나, 데모 계정에만 허용한다.
- 데모 데이터는 실제 데이터와 구분한다.

### 구현할 때 결정할 것 (❓)
| 항목 | 쟁점 | 결정 시점 |
|---|---|---|
| **JWT 저장 위치와 Mustache 화면** | Mustache는 서버가 화면을 그리므로 페이지 이동 시 `Authorization` 헤더가 붙지 않는다. HttpOnly 쿠키에 JWT를 두는 방법 vs 화면은 껍데기만 두고 JS `fetch`로 API 호출하는 방법. 쿠키는 CSRF, localStorage는 XSS 위험 | 3주차 (JWT 도입 전) |
| **SSE 연결 인증** | 브라우저 `EventSource`는 헤더를 못 붙인다. 토큰을 URL에 넣으면 로그에 남는다. 쿠키 사용 or 짧은 수명의 SSE 전용 토큰 | 8주차 |
| 로그아웃/토큰 무효화 | JWT는 서버가 만료 전에 못 막는다. 만료 시간을 짧게 + 필요하면 Redis 블랙리스트 | 3주차 이후 |
| 어뷰징 방지 | 다중 계정으로 대기 선점, 등록 API 폭주. Redis 기반 요청 횟수 제한(Rate Limit) | Optional |
| 번호 도용 | 번호만 입력하므로 남의 번호로 대기를 걸 수 있다. 현장 태블릿에서만 입력 가능하고 제재가 연속 5회부터라 장난 한두 번은 걸리지 않는다. 인증번호 단계는 문자 구현체를 붙일 때 Optional로 추가. 다중 계정 방어는 Rate Limit(Optional) | 7주차 |
| HTTPS | 로그인 토큰 보호를 위해 배포 시 인증서 필요 | 11주차 |
| 의존성 취약점 | GitHub Dependabot 켜기 | 1주차 |
| Actuator/Swagger | 쓴다면 운영 배포 시 접근 제한 | 배포 전 |

## 9. 확정 사항 (2026-10-27, 일부 10-30 변경)

1. **접수 시간**: Core는 수동 열기/마감만 구현하고, 요일별 스케줄과 날짜 예외는 Optional로 미룬다. 스케줄을 도입할 경우 가게가 요일별 접수 시간을 설정하면 자동으로 열리고 닫힌다. 특정 날짜는 예외(조기 오픈/조기 마감/휴무)로 수정한다. 가게는 언제든 수동으로 열고 닫을 수 있다. (P-4, P-5, W-11, R-11)
2. **동시 대기**: 서로 다른 팝업에는 동시에 대기할 수 있다. 같은 팝업은 1인 1대기, 중복 방지 기준은 (회원, 팝업). (R-9)
3. **회원 전용**: 전화번호 계정으로만 대기한다. 처음 등록하면 자동 가입된다. (R-8) *(10-30 변경: 이메일 가입 → 전화번호 간편 가입)*
4. **노쇼 처리**: 시스템이 자동으로 처리하지 않고 운영자가 직접 체크한다. 체크하면 다음 팀이 호출된다. 호출 5분 경과 시 운영자 화면에 표시만 한다. (W-9, W-9a, R-4)
5. **노쇼 제재**: 연속 노쇼 횟수를 기록하고, 정상 입장 시 리셋, 사용자 취소는 영향 없음. 3·4회째 경고 알림, 5회째에 다음날부터 7일간 신규 대기 불가(기존 대기 유지), 제재가 끝나면 횟수 리셋. (B-1~B-4, R-10)

6. **대기번호 날짜 기준**: 자정에 리셋한다. 자정을 넘겨 마감하는 팝업은 마감 시각을 날짜 경계로 쓴다. (P-6, R-7)

7. **위치 검증 대신 가게 태블릿**: 위치는 조작될 수 있고 실내에서 부정확하므로, 등록을 가게 태블릿(STORE 로그인)에서만 받아 현장 진입을 확인한다. QR 토큰은 사진 공유로 뚫려 폐지했다. (P-2, W-1) *(10-30 변경)*
8. **역할 3종**: USER / STORE / ADMIN. 가게 1곳에 가게측 계정 1개. 가게측은 별도로 가입하고 ADMIN 승인 후 사용한다. (U-3~U-5)
9. **ADMIN/STORE 분리** (10-30): ADMIN은 가게 관리(승인·거절), STORE는 자기 가게 운영. ADMIN은 가게 운영 API를 쓰지 않는다.
10. **회원 탈퇴** (10-30): Core, 맨 뒤 순서로 구현. WAITING만 있으면 취소 후 탈퇴, CALLED가 있으면 탈퇴 불가. (U-6)

### 구현할 때 확인할 가정
- 수동 조작은 다음 스케줄 전환 시점(다음 자동 열림/닫힘)까지 유지되는 것으로 가정한다. (더 단순한 방식이 있으면 변경)
- 두 팝업에서 동시에 호출돼 노쇼가 쌓여도 별도 처리하지 않는다. (사용자 책임)
