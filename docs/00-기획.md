# OpenRun 기획 (1페이지)

## 한 줄 정의
팝업스토어 현장에서 가게 태블릿으로 **원격 줄서기**를 접수하고, 순번에 맞춰 알림을 받는 **Redis 기반 대기열 플랫폼**.

## 만드는 이유
- 포트폴리오의 핵심 주장: **"동시 요청에서 대기번호가 중복·누락되지 않도록, 채번 방식을 비교하고 직접 해결했다."**
- 기능 개수가 아니라 이 한 가지 깊이로 승부한다.
- 서비스 성격: 사전 예약이 아니라 현장 줄서기(테이블링, 캐치테이블 방식). 정원이 없고 대기열이 계속 늘어난다.

## 타겟 사용자
- 일반 사용자: 현장 태블릿에서 전화번호로 대기 등록, 내 순번 확인, 알림 수신
- 운영자: 대기 현황 확인, 다음 팀 호출, 입장 처리
- 면접관: 데모 패널로 가입·현장 방문 없이 전 과정을 체험

## 제약 조건
- 기간: 약 12주 (여유 시 14주까지), 학원 병행
- 인원: 1명 (LLM과 학습하며 개발)
- 회사 제출용 저장소에는 LLM 지침 파일을 올리지 않음

## Core 기능
1. **회원/인증**: 손님 전화번호 간편 가입, 로그인, Spring Security + JWT, USER/STORE/ADMIN 역할, 가게측 가입과 운영자 승인, 회원 탈퇴(맨 뒤 순서)
2. **팝업스토어**: 목록/상세 조회, 접수 열기/마감, 가게 태블릿 접수 화면
3. **대기 등록**: 가게 태블릿에서 전화번호로 등록, 팀 인원 1~4명, 한 사람 한 팝업 1대기
4. **대기번호 채번 비교 (핵심)**: DB `MAX+1`(락 없음) → 비관적 락 → 낙관적 락 → Redis(`INCR`/Sorted Set), k6로 수치 비교
5. **대기열 운영**: 순번 조회, 취소, 호출, 입장 확인, 운영자 노쇼 체크(체크하면 다음 팀 호출), 호출 5분 경과 표시, 연속 노쇼 제재(5회 시 7일 신규 대기 불가)
6. **알림**: `NotificationSender` 인터페이스 + SSE + 로그
7. **데모 패널**: 원클릭 데모 로그인, 가상 대기자 생성, 동시 등록 시연, 다음 팀 호출
8. **보안 기본기**: 본인 데이터만 접근, 입력 검증, 시크릿 분리 (`01-요구사항.md` 8장)

## Optional (Core 완료 후 여유가 있을 때만)
- 요일별 접수 스케줄 + 날짜별 예외 (기본은 수동 열기/마감)
- Redis TTL 기반 정밀 노쇼 처리
- Rate Limit (어뷰징 방지)
- 확장: 선착순 이벤트(쿠지 등 정원 있는 대기, 예약금은 가짜 결제 상태값만) — 일정에 넣지 않고 시간이 되면 한다. 안 되면 하지 않는다
- 문자(SMS) 발송 구현체 (`NotificationSender`에 추가, 인증번호 단계도 함께)
- 공공데이터 연동(팝업 정보), AI 취향 추천
- 모니터링(Actuator + Grafana)

## 범위 밖 (하지 않음)
- 실제 결제(PG 연동), 시간대 예약, 카카오 알림톡 발송, 복잡한 관리자 기능, 이전 주제(식단, 밀키트, 타임딜)

## 일정 (12주)

| 주차 | 목표 | 완료 기준 |
|---|---|---|
| 1 | 요구사항/설계(ERD, API), 저장소, Docker(MySQL, Redis), 프로젝트 생성, 라이브러리 호환성 확인 | 서버가 뜨고 DB·Redis 연결 |
| 2 | 회원, 팝업 조회, 기본 대기 등록(DB `MAX+1`, 락 없음), JUnit 기초 | 대기 등록 API 동작 |
| 3 | Spring Security + JWT, 역할 구분, 본인 데이터 접근 검증 | 로그인 후 토큰으로 등록 |
| 4 | 동시성 재현(스레드 100개): 번호 중복·중복 등록. 비관적/낙관적 락, 유니크 제약 | 문제 재현 후 해결 |
| 5 | Redis 기초, `INCR`/Sorted Set 채번, Redisson 락, k6 비교 | 방식별 수치 표 완성 |
| 6 | 대기열 완성: 순번 조회, 취소, 호출, 입장, 상태 전이 | 상태 전이 테스트 통과 |
| 7 | 노쇼 체크·제재 | 노쇼 체크 시 다음 팀 호출, 연속 5회 시 7일 대기 불가 |
| 8 | 알림(`NotificationSender`, SSE, 로그) | 순번 변동이 화면에 실시간 반영 |
| 9 | 데모 패널, 최소 프론트(Mustache) | 면접관 시나리오 시연 가능 |
| 10 | 테스트 보강, 보안 점검, 리팩토링 | 핵심 로직 테스트 통과 |
| 11 | 배포(HTTPS), CI(GitHub Actions) | 외부에서 접속 가능 |
| 12 | README, 트러블슈팅 문서, 시연 GIF, 회고(KPT), 버퍼 | 제출 가능 상태 |

주차가 밀리면 Optional을 먼저 버리고, 그다음 9주차 프론트를 줄인다. **4~5주차 동시성 실험은 줄이지 않는다.**

## 데이터 (초안, ERD 단계에서 확정)
- DB(MySQL): `User`, `PopupStore`, `Waiting`(대기 이력과 상태)
- Redis: 팝업별 대기열(Sorted Set), 대기번호 카운터
- DB와 Redis의 역할 분담과 정합성은 5주차에 확정한다.
